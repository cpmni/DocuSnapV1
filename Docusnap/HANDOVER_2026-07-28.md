## Import performance (owner hit a slow 900-doc import, 2026-07-28 ~19:00) — DIAGNOSED, no code change
Measured ~3.1 s/doc (200 docs/623 s), all single-page synthetic scans. Machine: Ryzen 7 6800H (8 physical /
16 logical cores), 15.2 GB RAM, only ~3.7 GB free. **PRIMARY cause: `processing_concurrency=10` on a RAM-tight
box** — 10 extraction workers (each buffers 300-DPI images) + 6 pre-pass workers vs 3.7 GB free → memory
pressure, effective parallelism ~3 (bursts of 3 docs/sec), and the code's own warning (`handler.js:499`) that
at 10 the single-threaded persistence step is the wall. **CORRECTION (an earlier claim in this session was
WRONG): the separation pre-pass does NOT double-OCR single-page docs.** `segmentation.detect_segments`
(`ocr/segmentation.py:145-150`) reads page count from the PDF structure (no OCR) and early-returns "single
page" at `n < 2` BEFORE the render/OCR loop (`:163-169`). So the 2×-OCR only applies to genuinely multi-page
PDFs. What the pre-pass DOES cost on a single-page batch (runs because 22 templates + `auto_separate_enabled`
default ON, `handler.js:1052`): one short-lived Python spawn PER FILE to read page count (~0.3-0.5s cold-start
each, 6-parallel ≈ ~1 min / 900 files) — wasteful, not a doubling. RULED OUT: audit tamper-chain (1 row/5 min),
Tesseract thread thrash (pool caps OMP to cores/shards = 1/worker, `handler.js:1106-1115`), this session's
changes (none touch import).
**UPDATED DIAGNOSIS after live measurement (owner: "6 threads still slow; 10 used to run perfectly"):**
NOT a code regression. (a) The acute slowness was RESOURCE STARVATION — Chrome held ~2 GB and free RAM was
3.7 GB, so the worker fleet couldn't run; closing Chrome (→5.9 GB free) + concurrency 10 restored a healthy
fleet (10 python + 8 tesseract parallel, ~1.5 s/doc). (b) **CORRECTED the "lower threads" advice — it was
WRONG:** measured Tesseract = ~3.7 s/page at 300 DPI and it does NOT parallelise a single page (3757ms @ 1
thread ≈ 3656ms @ 8), so each doc is a fixed single-threaded job → MORE parallel workers = faster, not fewer.
Put `processing_concurrency` back to the core count. (c) **Root inefficiency: OCR renders every page at a
hardcoded 300 DPI (`ocr/tesseract.py` `_RENDER_DPI`) but the synthetic corpus is generated at 150 DPI
(`test_harness/config.py:23`)** — so a 2× upscale, paying 4× the OCR cost (scales ~DPI²) for zero extra detail
(measured 150 DPI = 1.3 s vs 300 = 3.7 s). NOTE the owner's "reads well at 108 DPI" = the REVIEW PREVIEW render
(`render/pages.py:74`, display-only), NOT the OCR — display-legible ≠ OCR-accurate; don't set OCR below 150.

**BUILT this session — configurable OCR render DPI (default 300 = byte-identical):**
