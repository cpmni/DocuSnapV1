## (2) CHRIS ROUND-5 FIXES — five cards, all committed (`ef7a3a5`)

### Card 1 (his worst — DATA LOSS) — ROOT CAUSE FOUND AND FIXED
A soft-deleted document, after the app is closed and reopened, came back on Restore as a **record with
no page**, and Confirm & File stayed enabled. Root cause (a read-only subagent trace, confirmed at
source): **`reconcileHolding` (`src/modules/processing/handler.js`) had `DEAD = {'confirmed','deleted'}`
and unlinked a deleted doc's inbox working copy on EVERY startup/after-batch** — while `softDelete`
keeps the file and its `working_path` pointer (its own promise: *"the file(s) are KEPT"*), and
`sweepInboxOrphans` protects deleted docs. A same-session delete→restore worked; the next launch culled
the file, leaving a stale pointer. THREE things done:
- Removed `'deleted'` from `DEAD`. A soft-deleted copy now survives until the bin is EMPTIED
  (`_purgeOne` deletes the row, so the next reconcile collects a true orphan). `'confirmed'` stays —
  those copies are unlinked + `working_path` nulled at confirm time, so any leftover is real debris.
- **Guard, regardless of cause:** `reviewService.confirm` now REFUSES a page-less doc BEFORE the claim
  with a friendly `NO_SOURCE_FILE` message (covers desktop, File All Ready, and /v1); the Review
  renderer disables Confirm and shows *"The scanned page … is no longer available"* instead of a bare
  *"No preview available"*.
- **Pins strengthened to RED-PROVE it:** `test_reconcile_holding.js` and
  `test_working_copy_durability.js` now assert a deleted copy is KEPT (neither tested a deleted doc
  before — the bug was untested); `test_reviewservice.js` gains a `NO_SOURCE_FILE` pin.
