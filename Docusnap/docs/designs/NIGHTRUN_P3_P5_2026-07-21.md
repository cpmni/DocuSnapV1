## P3 — the first-run wizard's 12-second self-close timer

### Root cause (verified; full trace in `HANDOVER_2026-07-21_LATE.md` §3)
`openMainShell()` (`src/main.js:204-224`) builds `teardown = () => { destroyWindow('login'); destroyWindow('license'); destroyWindow('onboarding'); }` and arms BOTH `main.once('ready-to-show', teardown)` (line 216) AND `setTimeout(teardown, 12000)` (line 217). Confirmed facts:
1. The timer handle is never stored; there is no `clearTimeout` for it anywhere.
2. `teardown` captures no window handle — `destroyWindow('onboarding')` resolves `windows['onboarding']` **at fire time**, so it destroys whatever wizard exists 12s later, including one created *after* the timer was armed.
3. `destroyWindow` sets `_allowClose=true` before `close()`, so this is a real DESTROY (not a hide-to-tray).
4. On a re-run the main shell already exists, so `createWindow('main', …)` takes the **reuse branch and returns at `main.js:526` without reaching `loadFile` (`:581`)** ⇒ `ready-to-show` can never re-fire ⇒ the 12s timer is the ONLY teardown that runs.
5. `onboarding-complete` (and Skip) call `openMainShell()` but never close the wizard themselves, so the wizard stays on screen and clickable until the timer fires mid-interaction.

### Fix (build directions 1–3 are self-contained `main.js`; direction 4 touches the shell swap → run past **eric**)
1. **Reuse-branch synchronicity.** Have `openMainShell` run `teardown` **synchronously** when `createWindow('main')` returned via the reuse branch (shell already painted), instead of arming a 12s delay. Detect "reuse" by capturing `const existed = !!windows['main'] && !windows['main'].isDestroyed()` *before* the `createWindow` call.
2. **Identity-scope `teardown`.** Capture the actual `BrowserWindow` instances at call time and destroy only those exact instances if still alive — an older timer can then never hit a newer wizard. Needs a by-instance variant of `destroyWindow` (e.g. `destroyWindowInstance(win)` that only closes if `windows[name] === win`).
3. **Store + clear the handle.** Save the `setTimeout` handle; `clearTimeout` it inside the `ready-to-show` arm and on main's `closed`.
4. **(eric) `onboarding-complete` owns its window.** `ipcMain.on('onboarding-complete')` (`main.js:~1302-1316`) should destroy the onboarding window itself rather than relying on the generic delayed sweep — the signal's window should not outlive the signal. This is the tidiest fix but touches the shell-swap ordering; eric must confirm it doesn't reintroduce the blank-swap flash the 12s backstop was added to prevent.

### Gate
The corpus gate is **blind** here (renderer/main lifecycle). Proof is the two zero-code owner observations in the LATE handover §5.2 (Skip → wizard sits ~12s then vanishes; reopen shows same-step-with-choices ⇒ hidden vs fresh-at-step-1 ⇒ destroyed). Pin what is unit-testable: that `teardown` after identity-scoping only closes the instance it captured (a small main-process unit test with a fake window map). **⚠ renderer edits to onboarding/login/license/main need a FULL APP RESTART** (the reuse-without-`loadFile` seam), so the owner must restart to confirm.

### Separate but related (do NOT fold in blindly)
The reuse-without-`loadFile` seam (`main.js:511-527`) also means a *hidden* wizard reopens on its stale step with stale renderer state ("Re-run setup reopens a stale wizard"). Fixing the timer does not fix that; `showOnboarding` should reload/reset on reuse. Log separately.

## P4 — field order unstable across documents

### Root cause (verified)
`getWithExtractions` (`database/modules/documents.js:122-134`) returns extractions `ORDER BY rowid` (`:126`) = the order the **Python engine emitted fields for that doc**, which varies by which stage won — so display order is arbitrary per document. `fields.sort_order` **already exists** (`database/index.js:1205`, default 100) and is the intended canonical order.

### Fix (order by the type's `sort_order` at the SHARED seam)
Order displayed fields by the document type's `fields.sort_order` (fallback `rowid`, then `field_key` for stability) at ONE shared seam so Review / Search / detached client all agree. Candidate seam: a shared ordering helper applied where extractions are joined to their field definitions for display — either inside `getWithExtractions` (join `fields` on `(document_type_id, key)` and `ORDER BY COALESCE(f.sort_order,100), e.rowid`) or in a shared projection used by all three surfaces.
- **⚠ `/v1` DTO contract.** Check `src/modules/api/handler.js` (`API_CONTRACT_VERSION`, the DTO projection + its conformance test) before changing client-visible ordering — the detached client may rely on the current order; a reorder is a contract-observable change even if no forbidden field is added. Version-bump the contract if the client asserts order.
- Structural roles (issuer/date/ref) must stay **reorderable-but-never-deletable** — do not special-case them out of the sort; they carry a `sort_order` like any field.
- Fields with no extraction row must still be handled the same as today (don't drop or reorder blanks unexpectedly).

### Second slice (do NOT start same night)
A drag-to-reorder editor in the Doc Type settings that writes `sort_order`. Separate build.

### Gate
`realdoc_regression` is blind (renderer/DB display change). Gate = a JS/DB unit test asserting a fixed (type, fields-with-sort_order, extractions-in-scrambled-rowid) input yields sort_order-major order across the shared seam, plus the `/v1` DTO conformance test staying green (or intentionally bumped).

## P5 — Template Manager alphabetical (Admin viewer only)

### Root cause / SEAM (verified)
`templates.getAll` (`database/modules/templates.js:28-42`) already serves live confirmed counts and sorts `confirmed_count DESC, name` (kill switch `TEMPLATE_LIVE_COUNTS`). **⚠ That same `getAll` feeds the sibling tiebreaks and "the order templates reach the matcher"** (`277a107` / `TEMPLATE_LIVE_COUNTS`) — so the SQL ordering is load-bearing for matching, NOT just display.

### Fix (do NOT re-sort the query)
Sort **in the Admin Template *viewer* only** — either apply the alphabetical (or user-chosen) sort in the settings renderer that renders `#tpl-dock`, or add an explicit `displayOrder` argument to a viewer-only wrapper that leaves the matcher-facing `getAll` byte-identical. Never change the ordering the matcher consumes.
- Owner's ask is "alphabetical" for the viewer. Offer name-A→Z as the viewer default with the current count-desc available, or just switch the viewer to alphabetical — an owner UI-preference call.

### Gate
Pure display; the invariant to protect is that `getAll`'s returned order (as the matcher sees it) is unchanged — a unit test pinning `getAll` order stays green; the viewer sort is applied downstream.
