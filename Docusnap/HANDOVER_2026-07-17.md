## ⚠ POST-BUILD REGRESSION — FOUND + FIXED (commit `5d5fd8c`, 2026-07-17)
The owner installed the first build (`e2a197e`) on a second PC and reported **Straighten says "this page
already looks straight" on a visibly-skewed page.** Root cause (traced, not guessed): my draw-tool refactor
`81a967d` added a bare **`import region_core`** to `ocr/region.py` and `ocr/region_worker.py`. Dev's system
Python auto-adds the script's own dir to `sys.path`, so every dev test passed — but the **packaged build's
EMBEDDABLE Python** uses a `python312._pth` that **suppresses the automatic script-dir on `sys.path`**, so
`import region_core` raised `ModuleNotFoundError` and crashed the script *before main()*. That broke, in the
built app ONLY: the **Straighten** button (`--deskew`), `--skew`/`--boxes` label capture, AND the **⊕ draw
tool** (warm worker + cold fallback). Proven by running the **actual `vendor/python`** on the bundled
`region.py` → crash; after fix → `{"angle": 2.0, "image": …}`.
**Fix (`5d5fd8c`):** add the script's own dir (`ocr/`) + parent (`python_backend`) to `sys.path` before the
import, in both files. Verified 4 ways: dev-normal, dev `-P` (PYTHONSAFEPATH = the embeddable behaviour),
bundled-python `region.py --deskew`, bundled-python `region_worker.py` (reaches ready). Regression pin:
`python_backend/tests/test_region_embeddable_import.py` (runs both under `-P`; 4/4). Detector itself
(`detect_skew_angle`) was always correct — worksheet_18 = 2.0° at the app's exact 108-DPI preview scale.
**DURABLE LESSON:** the packaged app's embeddable Python drops the script-dir from `sys.path`; any spawned
CLI script must `import` siblings via `from ocr.x import …` after a `sys.path.insert`, never a bare
`import x`. Reproduce/guard in dev with `python -P`.
**A SECOND installer was rebuilt** with this fix: **`dist\ScanFinder Setup 2.0.0-r20260717-0828-5d5fd8c.exe`**
(supersedes `…-r20260717-0754-e2a197e.exe`). Verified: the actual bundled `vendor/python` on the just-built
`region.py --deskew` returns `{"angle": 2.0, "image": …}`. **Owner: install THIS one on the second PC** (a
clean install is safest — fully quit ScanFinder first) and re-test Straighten + the ⊕ draw tool.

## FINDING (pre-existing gap, its own investigation)
**`logo_fingerprints.detail_hash` is NULL for ALL enrolled suppliers** (Ridgeway 5 prints, Marlowe) — the
confirm-time enrolment plants the 256-bit detail hash into TEMPLATES, not `logo_fingerprints`, so **Slice D
(the 256-bit logo resolver in `anchor.try_logo_supplier_match`) is partly INERT** for logo_fingerprints-based
matching. This is likely the DEEPER ROOT of the Marlowe/Ridgeway (and earlier Copperfield/Northgate)
collisions. The supplier pin fixes the doc but is NOT self-healing (documented). Fixing enrolment to populate
`logo_fingerprints.detail_hash` (and/or have Slice D read the template detail set) is the real cure — its own
design + Oracle pass.
